## 结论

当前主要问题是输入准备、L1到L0的转置装载和Cube到Vector的串行交接。矩阵乘法本身较短，优先改纯Vector或增加计算核数缺乏依据。现有核已经是Cube/Vector融合启动，但单个batch内部仍在完整矩阵乘及Fixpipe完成之后才启动Vector归约。

最小且值得先验证的改动是拆开A/B就绪依赖，让A的L1到L0装载有机会与B的GM到L1搬运重叠。其次研究B的LoadData遍历由16次减少为8次。更大的结构性候选是同一个batch内按64列流水化Cube和Vector；它有额外同步开销，不能直接承诺收益。

## 输入和实际路径

使用仓库自主构造的代表输入：B/M/N/K=16/32/128/256、FP16、TN。物理A为[16,256,32]，B为[16,256,128]，输出为16个FP32。不宣称复现官方隐藏形状或数值。

Host在32×128默认分块下命中CanBatchResidentTN，SelectKernelKey选BATCH_RESIDENT_TN，调用ComputeBatchResidentTN。Profiler实际核名为 `_ZN13batch_max_sum22ComputeBatchResidentTNEPhS0_S0_S0_jjj`，mix类型，Block Dim=16、Mix Block Dim=16。开发卡有20个Cube核，当前每个batch独占一组Cube/Vector，无跨batch求和，也不使用SyncAll。

每batch执行链：

1. A、B通过两条ND2NZ搬进L1；分别占16KiB、64KiB。
2. A用2条转置LoadData装入L0A，B按16个K分形循环，用16条转置LoadData装入L0B。
3. 一条MMAD完成32×128×256矩阵乘，FP32累加。
4. Fixpipe将16KiB结果写GM，然后设置跨核事件ID8。
5. Vector等待ID8，读回16KiB，将后64列逐元素Max折叠到前64列，执行32行WholeReduceMax，再WholeReduceSum，写回4字节。

总逻辑输入1.25MiB，中间矩阵一次写加一次读共512KiB，输出64字节。总矩阵乘约33.55MFLOP。每核L0A 16KiB、L0B 64KiB、L0C 16KiB；L0B已用满64KiB，不能直接给完整128列B再加一份L0双缓冲。逻辑字节数与实际缓存或HBM事务不是同一个概念。

## 模型定位与依赖问题

Ascend910B3软件模型，core0第二次调用。时间只用于分析依赖及指令，不代表9362硬件时间。各侧以其首条记录为零点。

| Cube阶段 | 起止时间μs |
| --- | ---: |
| A的ND2NZ | 0.435—0.668 |
| B的ND2NZ | 0.436—0.990 |
| 共18条LoadData | 0.992—1.328 |
| MMAD | 1.330—1.484 |
| Fixpipe | 1.487—1.699 |

Cube指令跨度1.708μs。A在约0.668μs已完成搬入，但其第一条LoadData直到0.992μs才开始。源码对应顺序为DataCopy A、DataCopy B、EnQue A/B、DeQue A/B，然后才LoadData A/B：A/B完成事件的提交与等待位置都阻止了A提前装载。

可实验改为DataCopy A后立即EnQue A，再DataCopy B并EnQue B；DeQue A后提交A的LoadData，之后才DeQue B并装载B。必须同时处理事件提交点和等待点，单纯交换LoadData文本顺序并不足够。保留MTE2→MTE1、MTE1→Cube和后续同步。此举不减少数据量；模型中A的两条装载覆盖约0.051μs，因此不能把0.324μs的就绪间隔全部视为可获得收益。

Vector模型：ID8等待约1.319μs；读回1.721—2.016μs；VMAX 2.018—2.061μs；VCMAX 2.063—2.200μs；VCADD 2.201—2.224μs；输出2.226—2.354μs。Vector指令跨度2.359μs。归约已经只有VMAX、VCMAX、VCADD各一条，优先继续削减归约指令的空间较小。

Cube统计18条LOAD_2D、2条ND2NZ、1条MMAD、1条Fixpipe，SET_FLAG/WAIT_FLAG各13次。每条LoadData的模型持续时间可能含排队并发生重叠，不把18条持续时间之和当作MTE1阶段耗时。

## 优化优先级和边界

1. **先做A提前装载的独立候选。** 目标是解除不必要的A等B依赖。仅改变ComputeBatchResidentTN内部调度，保持计算顺序和Host分派；用当前库做ABBA/反向交错对照。点5的B优先搬运曾无收益，但它是另一种调度，不能替代本路径验证。
2. **B的LoadData由16次变8次。** 按N分形遍历，repeatTimes=K/16、srcStride=1、dstGap=PAD_N/16-1；第nb次源为b1[nb*K*16]，目的为b2[nb*256]。逐分形地址推导与原布局一致，但仍需核实当前SDK接口、边界和真实收益。总搬运量不变；点5相似方案曾被用户因效果差撤回，不应直接迁移为已验证优化。
3. **同batch内按64列做C/V流水。** A完整驻留，B按列分块，使Vector处理前64列时Cube可以计算后64列，最后对两块行最大值取Max后再Sum。保留完整K的点积累加，不增加跨batch归约。总中间字节数不减少，MMAD、Fixpipe和事件数量增加；需要独立GM结果槽及正确的生产消费同步。收益必须实测。

不建议直接把每batch拆成两个独立核：16个batch会变成32个Cube任务，在20核卡上需要多轮，还新增行最大值合并。也不优先做纯Vector：当前Cube计算仅0.181μs，不能因为整核慢就推导为Cube算术不适合。

固定缓冲去队列可作为后续候选，但此前点5同类改动已有无收益或回退记录，不能仅凭模型Scalar指令减少就推荐合入。当前Vector中的secondBuffer/second未参与归约，是可清理项，尚无实测收益证据。

以上建议均应按布局、对齐、容量和分块条件适用，保留其他合法输入回退，不做测试编号或精确隐藏shape识别。每个候选单独验证，远端完整编译必须低于300秒。
