# BatchMatmulMaxSum 通用分派整改（2026-10-13）

## 目的与规则边界

按用户提供的[星辰杯算子开发规则 v1.0](https://gitcode.com/cann-competition/xingchenbei/blob/main/星辰杯算子开发规则_v1.0.md)审查并整改。本题链接属于上合赛区，本文不代替主办方对规则适用范围和最终合规性的判断。

重点处理 R3 所涉及的完整 shape/dtype/layout 白名单、R7 所涉及的测试用例定制实现、R6 所涉及的无计算启动，以及 A2 对可解释分块和正确回退的要求。仅改名字或删注释不能解决问题，本次同时修改核内寻址、循环、有效长度和尾块归约。

## 分派结构

1. 从公开元数据 B/M/N/K、dtype、转置属性和实际可用核数选择 ShapeKey，描述默认、紧凑、高窄、矮宽、均衡大矩阵或长K负载。
2. 按基本块、对齐、缓冲容量和任务覆盖条件生成 KernelKey。保持基础 tile 的编译期常量，完整逻辑尺寸由 Parameters 传入。
3. 通过 KernelKey 的 switch 启动对应核；不支持的布局/块参数转入通用32×128 Matmul核。通用核包含 FP16/BF16 × NN/NT/TN/TT 共8种实例。
4. 小型纯Vector和紧凑Cube路径仍在构造高阶Matmul tiling之前按容量类别分派，避免额外Host开销；它们也使用运行时尺寸，不保留完整形状匹配。

## 容量域与正确性约束

| 核类别 | 选择依据 | 核内泛化 |
| --- | --- | --- |
| 单点积 | FP16、B=M=N=1、K≤64，单个FP32 repeat | K运行时传入；对齐槽分别搬运，只在两个完整输入区间相邻且K对齐时合并；只启动1核 |
| 紧凑Cast/Gather | BF16 TN、B=1、M×N≤16、K≤64 | 动态M/N/K、输入偏移及128位有效Max掩码 |
| 小批量Vector | FP16 NT、B=2…4、M≤8、N≤16、K≤64且16对齐 | 沿用容量域内的实际形状循环 |
| 静态UB批量 | BF16 TT、B=2…4、M/N≤16、K为64或128 | M/N/K运行时，保留静态UB和分段归约 |
| 紧凑Cube | FP16 NN、B=5…8、M≤16、N≤32、K≤128且16对齐 | 完整K驻留，动态尾行/列 |
| 批量NT驻留 | BF16 NT、M≤32、32<N≤128、K≤256且16对齐，任务单轮覆盖 | B的头32列与其余列分别加载，NZ归约只使用有效N |
| 批量TN驻留 | FP16 TN、M≤32、N≤128、K≤256且16对齐，任务单轮覆盖 | N≤64不折叠，多余列仅归约实际范围；补齐M避免M=1触发不同硬件格式 |
| TT完整K驻留 | BF16 TT、大矩阵N分片；(128+112)×align16(K)×2≤512KiB，每片至多两个512列块 | 实际K、列片边界、行尾和列尾；连续MMAD显式满足L0C累加依赖 |
| 紧凑/扩展行块 | 每核均衡行数在(64,112]或(128,208]，相应NT/NN布局 | 基本块112或208，逻辑M/N/K动态；没有完整大矩阵尺寸常量 |
| TT交换表示 | FP16 TT、大矩阵N分片 | 从核数和列负载计算16对齐列片，C转置仅改变计算表示，保留原Max/Sum顺序 |
| 高窄驻留 | FP16 NN、B=1、N≤64、K≤128且16对齐，每核一个行片，tileRows≤512 | 行片按实际核数均衡，实际N寻址及归约，尾行补齐16 |
| 矮宽驻留 | BF16 NT、B=1、M≤64且16对齐、K≤128且16对齐、N为512整数倍，每核一个列片 | 实际M/K参与加载和归约；不满足对齐/覆盖条件使用分块核或通用核 |
| 长K驻留 | FP16 TT、B=1、M/N≤64、K≥4096，每片align16(K/cores)≤1024 | 实际M/N/K，256长K块和尾块；其他长K使用SDK分块 |
| SDK优化与通用核 | 基本块兼容性、布局和分片方式 | 支持实际尾块；无匹配优化域时计算完整数值结果 |

B=2…4、5…8等为批量负载区间，16/32/64/128/256/512等为指令对齐和容量/分块参数。分类域覆盖多个输入形状，域外不报“未编译”异常。基础块匹配用于保证编译期Matmul配置与运行时tiling一致，不用来识别某个完整输入。

已删除旧的禁用分发块和用例编号标识，移除MakeKernelMatmulConfig/MakeSplitKDualConfig里的完整固定M/N/K配置。没有加入Host数值计算、输入内容识别、输出常量或结果缓存。

## 验证方法

新增 tests/tiling_domains.py，涵盖容量邻域、对齐边界、回退、单行单列、全负和全零。复用独立FP64参考、两次输出一致性、输入不变、输出保护区检查，并使用 --capture 验证计算图重放。

真机首轮邻域测试发现TT短尾块L0C读写冲突。输出搬运方向的同步未解决该问题；连续MMAD之间补充PIPE_M依赖后通过。保留首轮失败记录，不将其计入最终通过结果。

性能基线为本轮改动前、已接通合法输入回退的源码，不是原始HEAD；其SHA256为 81b466110969ce0f6f7fb2f517642e5a6e0ddb67e33119be3dcfa63864e80911。对照采用同机、同输入，按布局分组交错ABBA/BAAB，20次预热＋50次采样，使用msprof task-time=l0的核时间，排除正确性校验和预热，不使用Python墙钟作为性能。

编译由远端Python子进程设置300秒超时，记录实际退出码、耗时、源码和共享库哈希。开发机远端编译结果与官方OJ编译分别陈述，未提交OJ不能称为通过官方编译验证。

## 证据与复现

证据位于[general-dispatch-20261013](evidence/general-dispatch-20261013/)。`audit.json`关联最终源码、远端编译与测试组数；`build.json`记录完整编译命令、时间及库哈希；`final-domains`、`final-capture`、`final-fallback`保存逐组原始JSON、日志和汇总。`precheck`、`check2`、`check3`及各阶段build目录保留失败和修复过程。

`performance/comparison.json`给出逐项汇总、每轮中位数、输入哈希和样本数；各组子目录保存应用校验报告、正式样本和原始`op_summary` CSV，已验证CSV哈希。原始二进制profiler数据留在远端工作目录，本地证据不重复存储。

证据中的`build.py`、`regress.py`、`performance.py`、`compare.py`在远端独立工作目录运行：目录中放置当前`src/`、`tests/`，基线库放置于`baseline/libcandidate.so`，加载CANN 9.0环境。性能脚本只对本地自主构造输入做测量；测试代码不参与提交算子的计算或分派。全部检查未修改官方测试环境，也未提交OJ。
