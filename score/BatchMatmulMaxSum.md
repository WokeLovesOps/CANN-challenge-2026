### 单变量实现与并行方式

本轮只增加一条按真实维度选择的小点积实现；`src/` 仅修改 `kernel.asc`。在 B=M=N=1 时，矩阵结果只有一个数，后续 Max 与 Sum 都是恒等操作，可以直接计算 K 个乘积之和。K 限制在已定向验证的 32–256 范围，两种输入类型先精确转换成 FP32，再用 Vector Mul 和 ReduceSum 并行完成乘法与归约。四种转置布局在这一退化形状下均为连续 K 个元素。

该场景用一个 Vector 核，核内通道并行；没有增加核数。将几十到几百个乘积跨核拆分会增加 partial 写回、同步和最终合并，本轮不采用。开发指南《CANN 社区版 8.5.0 Ascend C 算子开发指南》§3.6.3.1，正文 429–430 页（PDF 第 463–464 页）建议微秒级小任务权衡核数与头开销，并为纯 Vector 计算设置合适的 Kernel 类型。本实现显式设置 `KERNEL_TYPE_AIV_ONLY`，省去通用混合路径的 Cube/KFC 协作及中间 GM 结果。

输入使用 DataCopyPad 按 K×2 字节精确搬运，输出只写一个 FP32，K=40/248 不要求 GM 补齐；UB 总分配 4128B。Host 分支位于合法性检查之后，每次仅启动一个 ComputeDot，捕获期间不主动同步，没有新增临时 GM 工作区。K=264、B/M/N 任一不为 1 均走原 Compute；原 224B Parameters、自适应 N 分片和通用捕获工作区生命周期不变。没有依赖点号、输入数值、随机种子或预存答案。

最小用例第二次调用的模型指令表实际包含两条 VCONV、一条 FP32 VMUL、一条 VCADD；采集只有 Vector 核时长，未出现 MMAD。该证据支持选中核内向量并行路径；未将重叠指令周期相加来解释总耗时。

## 自适应 N 分片 `9f31802`（2026/09/15，本地模型）

### 单变量和指南依据

原分片策略在 `rowTasks = B * ceil(M/32)` 满足 `rowTasks * 4 <= availableCoreNum`，且 `columnTiles = ceil(N/128) >= 4` 时固定分成四片。当行任务很少、N 很长时，这仍会让大量核空闲。本轮保留上述触发范围，改为 `parts = min(availableCoreNum / rowTasks, columnTiles)`；否则仍使用一片。核数始终为 `min(availableCoreNum, rowTasks * parts)`，没有硬编码为 20。

内部 Host/Kernel 参数结构增加 `nParts`，配套调整分片编号、partial 布局和最终 Max 合并的片数；外部 `run_kernel` 入口签名不变。列块区间仍为 `[floor(columnTiles*p/parts), floor(columnTiles*(p+1)/parts))`，保证每片非空、列块数相差至多一块，任务总数不超过可用核数。每片保留原来的双 GM 槽流水和首块初始化方式。最终仍先合并同一行的各片最大值，再沿原行序求和；32×128 基础块、K 点积、行归约、单 kernel 启动及捕获工作区管理均沿用 `62bec9f`。`2e26435` 的 UB 累计改动已在独立提交 `7efb014` 中撤回。

依据 [《CANN 社区版 8.5.0 Ascend C 算子开发指南》](<../docs/CANN社区版 8.5.0 Ascend C算子开发指南 01.pdf>) §3.6.2.1 正文第 428 页（PDF 第 462 页）的核间负载均衡建议，并同时考虑 §3.6.3.1 正文第 429 页指出的核启动、取址和同地址访问开销。增加核数可能增加头尾开销，不能仅按核数比例预测收益，因此本轮没有扩大到原先不满足四路条件的小场景。

局部最大值仍为每片 128B，scratch 为每个核原来的双槽容量；扩核时总 scratch 和 partial 随片数增加。Finish 的读入 UB 为 `parts * 128B`，本题最多 64 个列块，因此其上限为 8192B。模型报告 20 个 Cube 核时，本轮实际最多 20 片、2560B；最终 Max 合并开销也随片数增加。

## 四路 N 分片 `62bec9f`（2026/09/15，本地模型）

### 单变量与适用条件

本轮只引入 N 轴的四路任务划分。Host 使用 `rowTasks = B * ceil(M/32)`、`columnTiles = ceil(N/128)`，同时满足 `rowTasks * 4 <= availableCoreNum` 和 `columnTiles >= 4` 才启用。核数来自调用者提供的 Cube 核数，模板入口和本地测试均查询 `ACL_DEV_ATTR_CUBE_CORE_NUM`；没有硬编码为 20，也没有将 Vector 核数当作 Cube 核数。未触发时编译选用 `SPLIT_N=false` 的原计算路径。

启用后，任务号映射为“行任务 × 4 + N 分片”。第 p 片处理列块区间 `[floor(columnTiles*p/4), floor(columnTiles*(p+1)/4))`，最后一片按实际 N 截尾。每片至少一个列块，块数相差至多一块。每片首块写本核 GM 槽 0，后续槽号按片内列块编号交替；异步提交的结束位置限于本片，避免越过分片或因非零起始列读错槽。

每个分片写回 32 个行最大值，占 128B；尾行补零但不参与最终 Max/Sum。0 号 Vector 核在原有 `SyncAll<true>()` 之后先逐行合并四个分片的最大值，再按原行序求行块 sum，将其放入 UB 中与基线一致的 16-float 间隔布局，最后沿用相同的 `ReduceSum` 顺序。最大值从每片第一列块初始化，保持全负值处理正确。没有提前对各片行结果求和，也没有切 K。

Cube 仍为 32×128，现有列块流水、批量行归约、单 kernel 启动和捕获工作区生命周期保留；没有同时引入 UB 常驻累计最大值或修改 Cube 基本块。启用分片的成本是核数增至原来的四倍、scratch 总量随之增加四倍，局部结果从每行任务 64B 增至 512B，以及一次跨分片 Max 合并。方案不保证所有合法形状或真实设备都获益。

## 行归约并行化 `2dcd5d4`（2026/09/15，本地模型）

### 单变量改动与指南依据

本轮只改变行最大值归约的执行方式。原实现每行调用 `ReduceMax(..., false)`，随后标量读取结果；除了显式 V_S/S_V，同一 API 在本地 CANN 的 `ReduceImplNoIndex`、`ReduceImplThirdStepNoIndex` 和尾部处理内部还插入 Scalar 同步。仅将外层等待移到循环外不能消除内部串行点。

候选使用 `WholeReduceMax(..., ORDER_ONLY_VALUE)`，以 `repeatTime=validRows` 一次下发多行归约；每行的前后至多 64 列分别归约，再用一次 Vector `Max` 合并。N 尾块通过两个连续 mask 限定，未引入补零。整块只显式等待一次 V_S，标量沿原顺序合并各列块的最大值，再用一次 S_V 保护下一块对结果缓冲的复用。行求和顺序、32×128 Cube 分块、核数、双 GM 槽流水、最终 Finish 及单 kernel 启动路径保持原样。结果 UB 从 32B 增至 128B，增加 96B；临时 UB 沿用已有容量。

依据 [《CANN 社区版 8.5.0 Ascend C 算子开发指南》](<../docs/CANN社区版 8.5.0 Ascend C算子开发指南 01.pdf>) 的正文页码：

- 第 20 页：各计算/搬运队列异步执行，Scalar 负责下发指令。
- 第 32 页：正向与反向同步须对应实际数据依赖。
- §3.6.4.2，第 436–437 页：异步 Matmul 减少 AIC/AIV 同步依赖，当前列块流水已采用该方向。
- §3.6.6.3，第 465–469 页：按数据规模选择归约指令，避免通用 Reduce 接口的额外开销。
- §4.4.2.6.4，第 875–878 页：float 连续 mask 不超过 64；`srcRepStride` 以 32B 块计，因此本实现为 16；仅输出最值时 `dstRepStride=1` 表示连续 float 输出。

实际接口与实现同时核对了本地 CANN 9.0.0 的 `asc/include/interface/kernel_operator_vec_reduce_intf.h`、`asc/impl/basic_api/dav_c220/kernel_operator_vec_reduce_impl.h`。PDF 的接口版本与本地编译版本分开记录。

## 本地重复调用修复

使用 `msprof op simulator --soc-version=Ascend910B3` 和同一最小 FP16 输入复现旧版本：第一次调用通过，第二次在 2 分钟限制处被强制终止。工具随后打印的 `All task success` 不是应用成功；日志缺少第二次通过和 `SIM_CORRECTNESS_PASS`，因此按失败记录。

旧版本的指令 CSV 显示，编译器初始化 KFC 区域时从 `0x1131a200` 开始清零，而 Matmul 通信轮询使用 `0x1231a200`。两者相差 `0x1000000`，即 16 MiB。第二次调用中 Vector 在 `0x1231a380` 的消息状态上反复轮询，Cube 已结束。Host 清零工作区不能修正核内通信地址选择错误。

`59b6005` 只修改注册处的工作区来源：保留 `__kfc_workspace__` 参数绑定，使用 `GetSysWorkSpacePtr()` 传给 `REGIST_MATMUL_OBJ`。直接使用绑定后的用户区形参会偏离系统通信区；删除参数绑定再调用 `GetSysWorkSpacePtr()` 也不是此次修复。修复后的两次轨迹均显示，清零与通信使用同一地址 `0x1131a200`。

## OJ Runtime Error 与捕获诊断

用户确认 OJ 全部 Runtime Error 对应 `59b6005`，测试点不可见，未提供运行日志。以下是本地定位出的入口兼容性问题，尚不能等同于 OJ 的已确认根因。

普通最小调用通过后，调用 `aclmdlRICaptureBegin(stream, 0)`，再执行原入口，出现：

```text
CAPTURE_BEGIN_CODE=0
terminate called after throwing an instance of 'std::runtime_error'
  what():  aclrtMemset: 107030
```

CANN 9.0 的 `acl/error_codes/rt_error_codes.h` 将 `107030` 定义为 `ACL_ERROR_RT_CAPTURE_MODE_NOT_SUPPORT`。该次应用退出状态为 134，详见 [旧版捕获崩溃](evidence/59b6005-capture-abort.txt)。

`c4878ab` 保留普通调用同步后释放的流程；捕获时不执行同步 `aclrtMemset` 或 `aclrtSynchronizeStream`，由核内初始化清理通信区，并通过 `aclmdlRIDestroyRegisterCallback` 将工作区持有到图销毁。计算公式、分块和精度实现未改变。

本地候选版本可以结束捕获，但重放后输出仍为保护区填充值，检查失败。关闭目标核采集后同样失败。独立的 AIV 常数写入对照核，普通执行输出 42，捕获目标为 43，重放后却仍是预填的 77；捕获、执行和同步 API 均返回 0。这个对照说明不能用现有软件模型流程宣称候选版本的图重放已通过。详见 [候选捕获日志](evidence/c4878ab-capture-simulator.txt)、[独立对照核日志](evidence/capture-control-simulator.txt)。对照源码保留在 `Build/CaptureControl20260915`。
