## 当前结论

最新本地候选为 `d8d8fc4`，在 `3fc5f47` 基础上重叠相邻列块的 Cube 计算与 Vector 搬运/归约。正式、诊断构建和四个定向用例通过，轨迹确认第二块 Cube 乘法在第一块 Vector 归约尚未结束时执行。尚无这两个候选的 OJ 成绩，平台最优继续保留 `a542170`。

最新平台基线为 `a542170`：用户反馈 2026/09/15 14:00:57 的 OJ 总分为 **16.97**，全部 15 点均返回有效用时。本次结果按紧接候选提交的会话上下文归属该版本。单核跳过跨核屏障、保留 `PipeBarrier<PIPE_ALL>()` 后，此轮未再出现此前的 Runtime Error；多核仍执行原有 `SyncAll<true>()`。这支持该修改解决了本轮平台执行问题，但没有设备异常明细，仍不能断言此前 507015 的底层机制。

此前 `b1eeb9f` 的 OJ 反馈：单 kernel 版本的测试点 1 在 DeviceProf 首次预热重放时返回 `aclrtSynchronizeStream: 507015`，进程退出状态 134。该旧版本不能作为通过 OJ 的基线。日志见 [测试点 1 原始反馈](evidence/b1eeb9f-oj-case1-507015.txt)。以下单启动修复的本地结果保留，但不等同于设备 profiling 重放通过。

用户补充的 OJ 错误为：`Profiling rule violated: each iteration must launch exactly 1 kernel. Expected 75 launches, got 150.` 当时已确认的错误是每次调用启动了 Compute 和 Finish 两个 kernel，违反平台单启动规则；不能再把此前的流捕获假设当作这条错误的原因。

`b1eeb9f` 将 Finish 改为普通核内函数。各 Vector 核写完 partial 后执行 `SyncAll<true>()`，由 0 号 Vector 核复用同一 TPipe 完成最终求和。Host 每次只启动一个 Compute，矩阵乘分块和行归约计算不变。同步只覆盖 Vector 侧，避免要求仍在 KFC 服务循环中的 Cube 参与屏障。

正式 CANN 9.0 / dav-2201 构建和诊断构建均成功。仅运行三个小型定向用例，每组连续两次，精度、逐字节重复一致性、输入不变和输出保护区全部通过；每组日志恰好两次 Compute 启动、两份非空 BIN。没有运行大规模矩阵、75 次重放或云端 NPU，该段为旧版本地验证记录；最新平台结果见下表。

先前发现的大 K 输入改写间歇失败和本地模型计算图重放限制尚未由此次小规模测试消除。历史硬件结果来自 CANN 8.5.2 / 910B3，不作为当前版本的硬件验证结论。`src/` 内仍只修改 `kernel.asc`，本地提交未推送。

## 列块双缓冲流水 `d8d8fc4`

本轮单变量为列块调度：N>128 时使用两个核私有 GM 结果槽，首块异步提交；每轮 WaitIterateAll 等待当前块结果完成，发起当前块的 GM→UB 搬运，然后向另一个槽异步提交下一块，再执行当前块的 Vector 归约。第三块复用第一槽时，第一块已完成搬运和归约。N≤128 保留同步路径。每核多列块 scratch 从 16 KiB 增至 32 KiB，UB 用量不变；矩阵乘 tiling、最大值和求和顺序、单 kernel 启动方式均保持原样。

接口依据为本地 CANN 9.0 的 `asc/include/adv_api/matmul/matmul_client.h`：异步 IterateAll 通过 waitIterateAll 参数请求完成通知，读取结果前显式 WaitIterateAll；异步模式的 End 不再发送同步模式的 END 消息。实现采用 `IterateAll<false>(destination, 0, false, true)`，不改变 ND 输出行距。

## DeviceProf 首次重放失败：定位边界

- 错误已从启动计数违规推进到实际设备执行异常。当前明确失败位置为 DeviceProf 的第一次预热重放；`times:5` 不代表五次预热已完成。
- `507015` 是 AICore 执行异常总码。当前反馈没有 `aic_error`、`vec_error_info`、`mte_error_info` 或异常 PC，无法据此区分访存、同步或重放参数故障。
- `aclrtSynchronizeStream` 只位于当前入口的非活跃捕获分支。本次错误与此前流捕获期间的 `107030` 不同，不能继续按捕获模式不支持同步来解释。
- 本地经过验证的设备 ELF 含对应 FP16 非转置入口的 `_mix_aic` 和 `_mix_aiv` 元数据，见 [静态核对结果](evidence/b1eeb9f-local-mixed-metadata.txt)。这排除了本地产物完全缺少 Cube 代码的猜测，但不能证明 OJ 产物及重放配置相同。
- 日志已明确基本信息采集失败，故末尾的 `Op Type: vector` 和空 `Mix Block Dim` 暂不能单独用于认定编译类型错误。`Task Duration=0` 不是有效性能结果。

上述定位记录对应 `59cf3ed`，当时仅做静态核对。用户随后确认平台只有当前日志，没有进一步设备异常明细；具体根因仍未确认。后续单核屏障对照见下节。

## 本地重复调用修复

使用 `msprof op simulator --soc-version=Ascend910B3` 和同一最小 FP16 输入复现旧版本：第一次调用通过，第二次在 2 分钟限制处被强制终止。工具随后打印的 `All task success` 不是应用成功；日志缺少第二次通过和 `SIM_CORRECTNESS_PASS`，因此按失败记录。

旧版本的指令 CSV 显示，编译器初始化 KFC 区域时从 `0x1131a200` 开始清零，而 Matmul 通信轮询使用 `0x1231a200`。两者相差 `0x1000000`，即 16 MiB。第二次调用中 Vector 在 `0x1231a380` 的消息状态上反复轮询，Cube 已结束。Host 清零工作区不能修正核内通信地址选择错误。

`59b6005` 只修改注册处的工作区来源：保留 `__kfc_workspace__` 参数绑定，使用 `GetSysWorkSpacePtr()` 传给 `REGIST_MATMUL_OBJ`。直接使用绑定后的用户区形参会偏离系统通信区；删除参数绑定再调用 `GetSysWorkSpacePtr()` 也不是此次修复。修复后的两次轨迹均显示，清零与通信使用同一地址 `0x1131a200`。

## OJ Runtime Error 与捕获诊断

用户确认 OJ 全部 Runtime Error 对应 `59b6005`，测试点不可见，未提供运行日志。以下是本地定位出的入口兼容性问题，尚不能等同于 OJ 的已确认根因。

普通最小调用通过后，调用 `aclmdlRICaptureBegin(stream, 0)`，再执行原入口，出现：

```text
CAPTURE_BEGIN_CODE=0
terminate called after throwing an instance of 'std::runtime_error'
  what():  aclrtMemset: 107030
```

CANN 9.0 的 `acl/error_codes/rt_error_codes.h` 将 `107030` 定义为 `ACL_ERROR_RT_CAPTURE_MODE_NOT_SUPPORT`。该次应用退出状态为 134，详见 [旧版捕获崩溃](evidence/59b6005-capture-abort.txt)。

`c4878ab` 保留普通调用同步后释放的流程；捕获时不执行同步 `aclrtMemset` 或 `aclrtSynchronizeStream`，由核内初始化清理通信区，并通过 `aclmdlRIDestroyRegisterCallback` 将工作区持有到图销毁。计算公式、分块和精度实现未改变。

本地候选版本可以结束捕获，但重放后输出仍为保护区填充值，检查失败。关闭目标核采集后同样失败。独立的 AIV 常数写入对照核，普通执行输出 42，捕获目标为 43，重放后却仍是预填的 77；捕获、执行和同步 API 均返回 0。这个对照说明不能用现有软件模型流程宣称候选版本的图重放已通过。详见 [候选捕获日志](evidence/c4878ab-capture-simulator.txt)、[独立对照核日志](evidence/capture-control-simulator.txt)。对照源码保留在 `Build/CaptureControl20260915`。
