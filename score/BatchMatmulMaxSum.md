## 当前结论

最新本地候选为 **`2dcd5d4`**：将逐行 `ReduceMax` 改为整块多行 `WholeReduceMax`，提升核内 Vector 连续执行能力并减少 Scalar 同步。正式构建、诊断构建和 16 个定向小用例通过，六个同批基线对照完成。当前没有该候选的 OJ 数据，平台最优仍保留第一行 `3effb7c`。

最新平台基线为 **`3effb7c`，17.69 分**：用户反馈 2026/09/15 14:45:41 的全部 15 点有效用时，按紧接隔离候选的会话上下文归属该版本。相对 a542170 总分增加 0.72 分（约 4.24%）；点 8–12、14 用时下降约 18.5%–38.6%，其余点变化在约 ±3% 内，单轮数据不足以区分小幅变化与运行波动。

`d8d8fc4` 此前首次预热重放返回 507015，而 `3effb7c` 保留双缓冲异步流水、仅撤回单任务直接输出后取得本次完整结果。这支持保留流水并恢复原最终归约的组合可在平台运行；故障范围更偏向直接输出路径及其与混合核执行的交互，不能据此断言提前 return、析构或某一条同步指令就是底层根因。3fc5f47 仍无独立 OJ 结果。

此前平台基线为 `a542170`：用户反馈 2026/09/15 14:00:57 的 OJ 总分为 **16.97**，全部 15 点均返回有效用时。本次结果按紧接候选提交的会话上下文归属该版本。单核跳过跨核屏障、保留 `PipeBarrier<PIPE_ALL>()` 后，此轮未再出现此前的 Runtime Error；多核仍执行原有 `SyncAll<true>()`。这支持该修改解决了本轮平台执行问题，但没有设备异常明细，仍不能断言此前 507015 的底层机制。

此前 `b1eeb9f` 的 OJ 反馈：单 kernel 版本的测试点 1 在 DeviceProf 首次预热重放时返回 `aclrtSynchronizeStream: 507015`，进程退出状态 134。该旧版本不能作为通过 OJ 的基线。日志见 [测试点 1 原始反馈](evidence/b1eeb9f-oj-case1-507015.txt)。以下单启动修复的本地结果保留，但不等同于设备 profiling 重放通过。

`b1eeb9f` 将 Finish 改为普通核内函数。各 Vector 核写完 partial 后执行 `SyncAll<true>()`，由 0 号 Vector 核复用同一 TPipe 完成最终求和。Host 每次只启动一个 Compute，矩阵乘分块和行归约计算不变。同步只覆盖 Vector 侧，避免要求仍在 KFC 服务循环中的 Cube 参与屏障。

## 行归约并行化 `2dcd5d4`（2026/09/15，本地模型）

### 单变量改动与指南依据

本轮只改变行最大值归约的执行方式。原实现每行调用 `ReduceMax(..., false)`，随后标量读取结果；除了显式 V_S/S_V，同一 API 在本地 CANN 的 `ReduceImplNoIndex`、`ReduceImplThirdStepNoIndex` 和尾部处理内部还插入 Scalar 同步。仅将外层等待移到循环外不能消除内部串行点。

候选使用 `WholeReduceMax(..., ORDER_ONLY_VALUE)`，以 `repeatTime=validRows` 一次下发多行归约；每行的前后至多 64 列分别归约，再用一次 Vector `Max` 合并。N 尾块通过两个连续 mask 限定，未引入补零。整块只显式等待一次 V_S，标量沿原顺序合并各列块的最大值，再用一次 S_V 保护下一块对结果缓冲的复用。行求和顺序、32×128 Cube 分块、核数、双 GM 槽流水、最终 Finish 及单 kernel 启动路径保持原样。结果 UB 从 32B 增至 128B，增加 96B；临时 UB 沿用已有容量。

依据 [《CANN 社区版 8.5.0 Ascend C 算子开发指南》](<../docs/CANN社区版 8.5.0 Ascend C算子开发指南 01.pdf>) 的正文页码：

- 第 20 页：各计算/搬运队列异步执行，Scalar 负责下发指令。
- 第 32 页：正向与反向同步须对应实际数据依赖。
- §3.6.4.2，第 436–437 页：异步 Matmul 减少 AIC/AIV 同步依赖，当前列块流水已采用该方向。
- §3.6.6.3，第 465–469 页：按数据规模选择归约指令，避免通用 Reduce 接口的额外开销。
- §4.4.2.6.4，第 875–878 页：float 连续 mask 不超过 64；`srcRepStride` 以 32B 块计，因此本实现为 16；仅输出最值时 `dstRepStride=1` 表示连续 float 输出。

实际接口与实现同时核对了本地 CANN 9.0.0 的 `asc/include/interface/kernel_operator_vec_reduce_intf.h`、`asc/impl/basic_api/dav_c220/kernel_operator_vec_reduce_impl.h`。PDF 的接口版本与本地编译版本分开记录。

## 列块双缓冲流水 `d8d8fc4`（平台反馈前的本地实验）

本轮单变量为列块调度：N>128 时使用两个核私有 GM 结果槽，首块异步提交；每轮 WaitIterateAll 等待当前块结果完成，发起当前块的 GM→UB 搬运，然后向另一个槽异步提交下一块，再执行当前块的 Vector 归约。第三块复用第一槽时，第一块已完成搬运和归约。N≤128 保留同步路径。每核多列块 scratch 从 16 KiB 增至 32 KiB，UB 用量不变；矩阵乘 tiling、最大值和求和顺序、单 kernel 启动方式均保持原样。

接口依据为本地 CANN 9.0 的 `asc/include/adv_api/matmul/matmul_client.h`：异步 IterateAll 通过 waitIterateAll 参数请求完成通知，读取结果前显式 WaitIterateAll；异步模式的 End 不再发送同步模式的 END 消息。实现采用 `IterateAll<false>(destination, 0, false, true)`，不改变 ND 输出行距。
