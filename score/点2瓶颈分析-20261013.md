# 点2瓶颈分析（2026-10-13）

## 结论

当前点2属于单核、BF16/TN、短K小输出的Vector路径。瓶颈更接近**前置参数/缓冲管理、索引生成及其同步串行化，加上固定搬运延迟**，不是矩阵乘算力不足或大流量HBM带宽饱和。Gather值得优化，但不能把整个耗时归因于Gather；已有一次合并Cast的开销很小。

本次仅分析及建立隔离对照，正式 `src/kernel.asc` 没有修改，其SHA256保持 `81954558a6c0e42b606f2726ea0654998ef060b5158dd95a9d4fde6ad8b657d0`。诊断核位于独立目录，不参与提交路径。

## 分析对象与计算量

点2对应 B=1、M=3、N=5、K=40、BF16、transposeX1=true、transposeX2=false。进入 `ComputePackedCastGather<bfloat16_t,true,false>`，只启动1个AIV。

- 输入A为120个BF16，输入B为200个BF16，共640字节；输出4字节。
- 15个点积共600次乘法，每个点积对40项求和；再做3组行Max和最终Sum。
- 紧凑输入转FP32后，3次A Gather与5次B Gather重排到64元素槽。
- 真机SoC报告 `Ascend910_9362`。软件模型为 `Ascend910B3`，二者的数据分别陈述。

## 真机流水计数

当前正式库的两次PMU采集给出：

| 指标 | 第一次 | 第二次 |
| --- | ---: | ---: |
| AIV计数时间 | 1.167μs | 1.818μs |
| Scalar计数时间/比例 | 0.810μs / 69.4% | 1.228μs / 67.5% |
| Vector计数时间/比例 | 0.447μs / 38.3% | 0.441μs / 24.2% |
| MTE2计数时间 | 0.294μs | 0.468μs |
| MTE3计数时间 | 0.095μs | 0.085μs |

这些流水并行，比例不可相加为100%，计数时间也不是普通msprof的整核Task Duration。第一次资源冲突计数中，Vector总冲突比例约0.62%，银行冲突约0.52%，不支持“UB冲突是首要瓶颈”的判断。

Profiler给出的“MTE带宽利用率低于80%”是阈值提示。对于640字节读取和4字节写回，应优先看固定延迟、指令发射和依赖链，不能仅据该提示判断需要增加内存带宽。

## 软件模型指令时间线

对当前核函数体的完整提取版本，第二次执行的指令跨度为0.970μs。以下时间仅用于定位依赖链，不代表真机或OJ耗时：

| 阶段 | 相对开始→结束μs | 区间长度μs |
| --- | ---: | ---: |
| 入口到首条输入搬运 | 0→0.213 | 0.213 |
| 两次输入搬运，彼此重叠 | 0.213→0.373 | 0.160 |
| 索引Vector计算：4次VADDS、2次VMULS | 0.383→0.455 | 0.072 |
| 合并Cast | 0.467→0.481 | 0.014 |
| 8次Gather | 0.484→0.643 | 0.159 |
| 3条重复Mul指令 | 0.644→0.695 | 0.051 |
| 15个点积的Sum | 0.697→0.775 | 0.078 |
| 3个行Max | 0.785→0.809 | 0.024 |
| 最终Sum | 0.812→0.835 | 0.023 |
| 输出搬运 | 0.837→0.965 | 0.128 |

入口到开始Gather已用去约0.484μs，占该模型完整指令跨度约一半。这个区间包含参数读取、初始化、搬运、索引及同步，不能全部记为TPipe初始化。模型中Gather本身约0.159μs，合并Cast仅约0.014μs，继续优先削减Cast的收益空间很小。

## 完整计算的隔离实验

全部有效对照均计算完整输出，未使用空核、截断计算或缓存结果。正式性能采样每组20次预热＋50次采样，按正序/逆序交错两轮；每种版本合并100个正式样本，确认输入哈希一致。只采用普通 `msprof --task-time=l0` 的Task Duration，PMU与软件模型不混作性能成绩。

第一组对照：

| 版本 | 合并中位数μs | 解释 |
| --- | ---: | --- |
| 当前完整正式库 | 1.660 | 原始代码 |
| 提取原核函数体 | 1.680 | 独立入口，有约0.02μs差异，后续变体与该提取基线比较 |
| 保留TPipe、去输入输出队列 | 1.680 | 无明显收益 |
| 仅改为直接位运算构造Max掩码 | 1.680 | 无明显收益 |
| 上述两项组合 | 1.680 | 无明显收益 |

第二组对照：

| 版本 | 两轮中位数μs | 合并中位数μs | 相对该组基线 |
| --- | --- | ---: | ---: |
| 提取原核函数体 | 1.690、1.690 | 1.690 | 基线 |
| 索引生成整体移到输入搬运前 | 1.760、1.720 | 1.760 | +4.14%，不推荐 |
| 显式索引生成与同步，移除TPipe及队列依赖 | 1.560、1.530 | 1.540 | −8.88% |

最后一项仍使用运行时M/N/K，先生成首个8元素索引块，经公开S_V事件同步，再分块递增形成完整K索引。它没有按3×5×40特判，也没有预存输入相关计算结果。8组额外真机检查覆盖16×1、2×8、1×16、1×1、4×4、5×3及全负/全零，全部通过；尚未完成正式集成后的全量回归、计算图验证和OJ测试，不作为已交付优化版本。

关键证据是该诊断版本的模型：输入搬运仍在0.216→0.375μs，索引计算却能在0.259→0.366μs与其重叠。Cast提前至0.376μs，Gather仍耗时0.159μs，整体指令跨度从0.970降至0.864μs。真机PMU第一次采集的Scalar计数从0.810降至0.517μs，而Vector计数约0.447→0.455μs。两者共同支持：收益主要来自减少控制开销和改善重叠，而不是加快乘法或Gather本身。

不能仅删除TPipe：CANN 9.0的 `CreateVecIndexOneBlk` 内部调用 `GetTPipePtr()->FetchEventID(HardEvent::S_V)`。最初直接删除TPipe的隔离版本真机输出校验失败；软件模型虽报告数值通过，仍出现 `invalid ldst addr`，已认定为无效，不使用其计时。证据保留于`timing/2-static_ub`和`model/model-static`。

## 预热与计时边界

20次预热后的正式样本存在明显两段分布：第一组每版本100样本中有38个超过2μs。原核合并中位数1.680μs、均值2.340μs；第二组原核均值2.328μs，诊断优化版本均值2.071μs。因此本报告同时保留全部样本，不挑选最低值，也不把中位数当作稳定且唯一的执行时间。

补充200次预热检查中，正式库50个样本中位数1.620μs、范围1.540～1.880μs；诊断优化版本中位数1.500μs、范围1.380～1.600μs，均没有超过2μs的样本。这支持存在预热敏感性，但不能单凭该现象断定是频率、缓存或运行时机制。结果另存`warmup200`，不替换上面的20＋50正式对照。无法仅凭这些本地数据解释用户OJ的3.40μs，OJ的设备、执行模式和计时口径需分别验证。

## 后续优先级

1. 优先将显式索引生成＋精简同步作为独立候选，保持整个BF16/TN小输出容量域可用；先验证完整库、计算图和其他类别无回归，再决定是否集成。
2. 其次研究Gather重复指令发射和布局；基线8次Gather约0.159μs，目标必须减少实际依赖链，避免为了合并Gather反而增加索引构造成本。
3. 暂不优先改Cast、Max掩码循环、增加核心数或换Cube；现有测量没有给出这些方向更高收益的证据。

正式代码本次未改变，其他测试点的分派和实现也未改变。未来集成必须继续满足远端编译≤300秒，并保留正确的通用回退。
