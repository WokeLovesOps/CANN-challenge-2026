# 条件写回探针运行异常排查

## 结论与边界

`9905ef0` 已由用户提供十五点全部通过结果；`44fe4f8` 相对通过源码只改两个最终写回表达式，却在 OJ 首次预热重放返回 507015。此次排查确认条件表达式改变了本地 Vector 指令与执行控制流，不能视为只替换最终数值。当前尚未获得 OJ 异常指令、异常地址、设备详细日志或平台编译产物，不能宣布底层根因已找到。

当前 `src/kernel.asc` 保持 `9905ef0` 原样，与 `16a8661` 逐字节一致。本轮未改代码、未新增提交平台的候选、未运行云端 NPU，也未重复已知受限的本地图回放。

## 已确认的差异

失败版普通归约把 `result.SetValue(b, reduced.GetValue(0))` 改为 `result.SetValue(b, batch == 1 ? 1.0e30f : reduced.GetValue(0))`；分片归约使用相同条件逻辑，batch 来自 `params.batch`。

C++ 条件表达式只求值被选中的分支，因此 B=1 时不再读取 reduced。仅先写 `float value = reduced.GetValue(0)` 再覆盖 value，也不能保证编译器保留这次读取。

对照 CANN 9.0.0 / dav-2201 两份正式产物，编译选项均为 `--npu-arch=dav-2201`，报错模板为 FP16、双不转置、SPLIT_N=false：

| 检查项 | 基线与候选对照 |
| --- | --- |
| 报错模板 AIC 函数 | 均为 17316 字节；只屏蔽重定位所在 4B 指令字并核对相对位置、类型、目标和加数后相同 |
| 报错模板 AIV 函数 | 7016→7032 字节；归一化后仍不同，变化不限于常量所在位置 |
| 入口 `.ascend.meta*` 元数据 | 全部相同 |
| `__CCE_KernelArgSize` | 相同 |
| `.ascend.stack.size.record` | 相同 |
| 全部 32 个计算入口 | 15 个 AIC 归一化后相同，另 1 个 AIC 不同；16 个 AIV 均不同。不能宣称整个 Cube 产物完全一致 |

函数与元数据相同只排除了对应本地产物中的差异，不能排除共享工作区、重放生命周期或平台工具链交互。

## 已有软件模型轨迹

使用同一 FP16、B=M=N=1、K=32 的普通调用轨迹，比较最终归约附近执行的指令：

| 操作 | 基线 | 条件候选 B=1 |
| --- | --- | --- |
| 最终 ReduceSum | 执行 | 执行 |
| 手写 V→S 事件 0 | 存在 | 存在 |
| 读取附近 V→S 事件 7 | 存在 SET/WAIT | 对应路径中没有 |
| 从 reduced 的 UB 地址读取 | 存在 `LD_XD_XN` | 跳过 |
| 输出 UB 写入 | 写入归约结果 | 写入 `0x7149f2ca`，即 FP32 1.0e30 |
| 手写 S→V 事件 0 | 存在 | 存在 |

事件 7 不来自这两行附近显式写出的事件 0，是编译产物中出现的额外同步。不能仅凭其在候选命中路径中消失，就认定其对正确执行必不可少。模型中的事件时间属于不同流水线，不能直接按时间排序推断全局发射顺序或死锁。

该本地候选普通调用成功写出错误常量，未触发设备异常；因此这份轨迹不是 OJ 故障现场。它证明读取与同步发生变化，尚未证明这些变化导致 507015。1.0e30 是有限 FP32 值，其写入本身不等同于触发硬件异常。

## 证据来源核验

基线历史轨迹来自 `Build/AdaptiveNAbiSmoke20260916/case0`，其源码与当前基线仅差文件末尾换行。为验证可比性，本轮新建 `Build/ProbeFailureBaselineDiag20260921`，使用当前基线及 `-g --npu-arch=dav-2201` 构建诊断库，构建通过。

新基线诊断库与历史基线轨迹导出的设备 ELF，32 个计算入口归一化后全部相同；候选诊断库与候选轨迹导出的设备 ELF，也全部相同。正式产物与诊断产物并不逐入口相同，不能把诊断轨迹当作正式产物的逐指令执行证明。

候选轨迹来自 `Build/BatchOneProbeChecks20260921/case0`。比较过程、提取 ELF 和脚本保存在 `Build/ProbeFailureAnalysis20260921`；结构化摘要及哈希见 [证据](../score/evidence/44fe4f8-runtime-analysis.json)。

默认 Python 缺少 pyelftools；使用已有 LLVM 工具提取 ELF、readelf 解析符号及重定位完成字节对照。LLVM 反汇编器返回 `<not available>`，未获得完整指令助记符反汇编；指令名称和数据来自已有模型轨迹，未将不可用的反汇编当作已完成分析。

## 下一步可区分的假设

最值得隔离的是“条件常量写回切断归约结果依赖，改变生成的读取与同步”。若后续继续实验，应保持最终输出依赖实际归约结果，再核验生成代码是否保留读取和相关同步，而不是仅把三元表达式拆成多行。即使该变化在 OJ 成功，也只支持这一修改组合，不能仅凭单次通过证明事件 7 是根因。

另一种可能是平台工具链、混合核重放或既有同步缺陷对代码布局变化敏感；现有材料不能排除。要定位底层异常，仍需设备异常明细或能在本地稳定复现的运行环境。507015 在本地头文件中定义为 `ACL_ERROR_RT_AICORE_EXCEPTION`，它不是具体越界、超时或同步错误的诊断。
